# Security Notes

- Firebase ID tokens are verified server-side with Firebase Admin, including revocation checks. The API then requires an active internal `User` row and uses its database-controlled `USER_A`/`USER_B` role; unprovisioned Firebase accounts are denied. The seed process can create Firebase accounts from the optional seed email/password variables, but never changes an existing account password.
- API and Socket.IO authenticate with verified Firebase tokens and database-provisioned identities. Company writes are User A-only, uploads are User B-only, and company/image access is constrained to persisted owner/collaborator relationships. The API has a global 60-request/minute throttle, strict DTO validation, Helmet headers, and exact-origin CORS.
- Logs are JSON and recursively redact fields whose names resemble tokens, authorization, passwords, secrets, cookies, email, or credentials. Do not add raw request headers, token claims, or uploaded content to logs.
- For the Supabase deployment, keep the Storage bucket private and keep `SUPABASE_SERVICE_ROLE_KEY` only in the Render API environment. The API accesses Storage server-side and redirects authorized reads to signed URLs that expire after two minutes. Never expose the service-role key to the browser.
- For the optional GCS deployment, enable uniform bucket-level access and public access prevention, grant the runtime identity access only to the application bucket, and configure signing permission as needed.
- The API authorizes every image request before redirecting to the short-lived Supabase signed URL. The browser then fetches from Supabase Storage, so verify signed-URL CORS from the deployed Vercel origin; if blocked, proxy the object bytes through the API instead of making the bucket public.
- Local image storage has directory mode 0700 and file mode 0600. Do not serve the storage directory as static content or place it under `public/`.
- The application does not include public account provisioning, password reset, invitation, or self-registration. The controlled seed provisions exactly one active Firebase-backed `USER_A` and one active `USER_B`; existing users can be selected by UID or email, and password changes are not performed.
- HTTPS is required in production. Cloud Run terminates TLS. Do not place service-account JSON, Firebase ID tokens, database passwords, or real `.env` files in source control.
